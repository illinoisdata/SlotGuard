# SlotGuard × NLIP：完整版论文研究计划

> 文档状态：研究设计草案，不是已实现功能清单，也不是实验结果。
>
> 工作定位：将 SlotGuard 从面向单个远端模型的 transcript 脱敏边界，扩展为面向 NLIP 多 Agent 协作的、任务与接收方感知的隐私及能力边界。
>
> 文档语言：中文。后续可以据此生成英文 proposal、论文大纲及项目 issue。

---

## 0. 执行摘要

### 一句话研究问题

**在跨信任域的 Agent 协作中，能否利用协议结构、本地小模型和确定性权限执行，在保持真实任务可完成性的同时，减少不必要的私有信息披露，并阻止受保护引用被越权使用？**

### 推荐主线

以 NLIP 作为协作与消息边界，以 SlotGuard 作为本地策略执行层，以轻量 System 1 模型作为语义判断组件：

1. **协议感知处理**：根据消息格式、子消息位置及信任属性，选择结构化解析或语义检测，而非对整个序列化 JSON 进行盲目替换。
2. **接收方绑定的引用与受控执行**：将受保护对象的引用绑定到经认证的接收方、会话和允许操作，原始映射留在所属信任域。
3. **任务感知的信息最小化**：用本地小模型识别规则难以处理的敏感语义和实体关联，但不允许模型自行授权或任意恢复原始值。
4. **真实端到端评估**：执行实际工具任务，联合衡量内容泄露、越权使用、任务完成率和完整系统延迟。

### 什么不算主要贡献

- 仅实现 NLIP adapter。
- 仅把 regex 替换成一个 LLM classifier。
- 仅增加 synthetic benchmark 数量。
- 把加密或身份认证等同于内容隐私。
- 因为引用有随机标识符，就称其为安全 capability。

### 最小可发表故事

即使不训练新模型，只要能证明：

> 在真实跨域任务上，协议结构与接收方绑定的执行控制，比文本级脱敏显著改善隐私—效用权衡，并避免可重复展示的转发、重放或引用滥用问题，

就可能形成一篇有价值的系统论文。是否加入专门训练的小模型，应由早期实验决定。

## 1. 与现有 SlotGuard 的关系

### 1.1 已有基础

当前稿件包含或描述了以下机制：

- typed、suffix-aware 的结构绑定替换；
- format-preserving synthetic substitution（FPS）；
- session-scoped slot table；
- 以关键词及模式关联为主的 semantic entity graph（SEG）；
- trusted runtime 内的 guarded rebinding；
- 规则检测和可选本地语义检测；
- 合成隐私语料、workflow probes 和 TAC-lite handle replay。

这些基础可复用，但应在实现审计中逐项验证，而不能直接把论文描述当成已经充分验证的实现保证。

### 1.2 完整版需要跨出的三步

| 维度 | 当前重点 | 完整版目标 |
|---|---|---|
| 保护边界 | 本地 runtime → 模型 provider | 本地 runtime → 协议端点 → 多接收方 Agent |
| 隐私策略 | 什么值需要隐藏 | 对谁、为哪个任务、在什么操作中可以披露什么 |
| 实体作用域 | 会话级 | 会话 + 经认证接收方 + 对象权限与生命周期 |
| 协议处理 | transcript 内容 | 消息、子消息、格式、会话及认证职责 |
| 语义能力 | 规则和简单链接 | 任务条件判断、别名与间接引用 |
| 评估 | 受控 probes / replay | 真实执行、跨域转发和攻击性重建 |

### 1.3 对当前论文的具体修补前提

在扩展前，先核实：

1. 64 个 invalid-rebinding checks 与 24 个 mixed hard cases 的测试来源和关系。
2. task success、execution-ready、tool-valid、invalid-handle 的真实评分规则。
3. 异步语义检测在 provider submission 前后的位置，是否存在首次出现时的泄露。
4. FPS 实际保留哪些信息，如何生成并避免映射歧义。
5. SEG 实际支持的编码、拆分及跨轮次形式。
6. 当前系统的所有网络出口和日志出口，避免只检查最终 prompt。

**交付物：** `CURRENT_SYSTEM_AUDIT.md`、可重复运行的测试、逐项定义的指标文档。

## 2. 论文定位与研究假设

### 2.1 推荐论文定位

**一种协议感知的本地隐私与能力边界，使跨信任域 Agent 能通过 NLIP 协作，而无需无条件共享原始本地上下文。**

### 2.2 候选英文标题

优先候选：

- **SlotGuard: Task-Aware Privacy and Capability Boundaries for NLIP Agent Collaboration**
- **SlotGuard: Protocol-Aware Information Minimization for Cross-Domain Agents**
- **Local Decisions, Bounded Disclosure: Privacy-Preserving Agent Collaboration over NLIP**

标题中是否保留 NLIP，取决于最终贡献是否依赖其协议特性。如果方法可迁移而 NLIP 只是一个实现载体，可使用更一般的标题。

### 2.3 三个主要假设

**H1：协议结构有助于实现更好的隐私—效用权衡。**

在匹配检测器、受保护对象清单和替换机制后，按消息类型及字段角色处理，比对序列化消息进行统一字符串替换更少破坏协议与工具语义。

**H2：接收方绑定与确定性授权能阻止单纯会话级 slot 无法阻止的引用滥用。**

具体包括跨接收方复用、跨会话重放、超范围操作和未经授权的转授权。这里检验的是引用与执行控制，不是宣称能阻止所有语义泄露。

**H3：本地语义模型可以改善规则覆盖不足的场景，但其收益必须覆盖延迟与过度脱敏成本。**

专用训练不是前提。若现成小模型已足够，则重点研究调度、校验、策略与系统集成；若误差有稳定结构，再考虑蒸馏和微调。

### 2.4 建议贡献表述

最终论文最好围绕三个贡献组织：

1. **问题与抽象**：区分跨域消息披露、端点到模型披露、引用可见性与执行权限。
2. **系统设计**：协议感知处理、任务感知本地建议、接收方绑定引用和本地授权执行。
3. **证据**：真实任务、强且公平的基线、适应性攻击、成本分析与可复现 artifact。

不要把 adapter、小模型、SEG、slot、调度分别包装成五个彼此松散的贡献。

## 3. NLIP 标准依据与设计边界

### 3.1 已查阅的依据

- NLIP 项目说明：<https://nlip-project.org/>
- ECMA-430：<https://ecma-international.org/publications-and-standards/standards/ecma-430/>
- 本计划所参考的基础规范：ECMA-430 第 1 版，2025 年 12 月。

ECMA-430 定义消息与子消息，以及 `text`、`token`、`structured`、`binary`、`location`、`generic` 等格式。`structured` 包括 JSON、URI、XML、HTML 及程序语言形式。

§6.2 对 token 子消息规定了响应中保持原值的要求及例外；conversation 和 authentication 前缀有特定用途。必须结合完整规范及具体 binding 实现，而不能仅凭本计划的摘要编程。

### 3.2 实现前必须补读并固定版本

- ECMA-431：HTTP/HTTPS binding。
- ECMA-434：security profiles。
- 所采用 SDK/reference implementation 的具体版本与 commit。
- 若确有必要支持 streaming，再阅读并采用 ECMA-432。

基础规范要求生产部署选择相应 security profile。不能只实现消息 JSON 就宣称完整安全合规。本计划尚未完成 ECMA-431/434 的逐条实现映射。

### 3.3 明确区分三类机制

| 类型 | 例子 | 论文中的表述方式 |
|---|---|---|
| 标准已有机制 | 消息格式、子消息、token 回传职责 | 指出规范条款与采用版本 |
| 实现层行为 | 哪些信息进入 LLM、日志如何处理 | 说明具体端点实现，不归因于标准 |
| 本研究扩展 | 接收方绑定 slot、隐私策略、执行权限 | 明确标为拟议扩展或应用 profile |

### 3.4 不能破坏认证语义

将凭据分为三种：

1. **通信端点被授权使用的认证材料**：由相应协议/security profile 处理，不能盲目 FPS。
2. **任务内容中意外夹带的本地秘密**：由 SlotGuard 检测、保护或阻止发送。
3. **端点需要处理，但背后 LLM 不需要知道的元数据**：保留在协议控制平面，不自动进入模型上下文。

任何中间层如果转换 token 或终止会话，必须作为显式协议端点实现并承担相应语义，而不是声称自己是透明的逐字节代理。

### 3.5 自定义扩展的路线

第一阶段优先采用 **endpoint 内部策略**，不修改基础 wire format。

若跨端点协商确有必要：

- 在规范允许的扩展点中定义应用扩展；
- 固定 extension 名称、版本、能力发现、拒绝与回退语义；
- 对不支持扩展的端点明确选择基础保护模式或拒绝敏感任务；
- 不把未知字段静默忽略当作安全协商成功；
- 不把协议 `token` 自动当作对象权限凭证。

**交付物：** `NLIP_CONFORMANCE_MATRIX.md` 和 `PRIVACY_EXTENSION_DRAFT.md`。

## 4. 场景、资产与威胁模型

### 4.1 最小三方场景

- **Local coordinator**：用户所属的编排 Agent，持有任务和隐私策略。
- **Remote worker**：跨信任域的分析或开发 Agent，通过 NLIP 接收任务。
- **Local execution service**：访问本地文件、运行工具，负责最终授权和原始值恢复。

扩展场景加入第二个 remote worker，用于研究跨接收方关联和任务转发。

### 4.2 保护资产

- 用户、组织、项目、客户、文档及内部环境标识。
- 文件路径、URI 中的受保护组件和敏感语义。
- API keys、passwords、tokens 等任务外秘密。
- 对象和实体在多轮、多接收方之间的关联关系。
- 本地对象的访问权限与使用范围。

### 4.3 两类主要对手

**隐私对手：** 能保留其收到的内容，并结合先验知识与全部可见 transcript 推断敏感值的远端端点或 provider。

**主动协议对手：** 可以生成恶意任务消息，尝试重放、转发、伪造引用、改变请求操作，或诱导披露额外上下文的远端 Agent。

两类对手可以分别评估。若评估接收方串谋，要单独声明并给出其能合并的视图。

### 4.4 信任假设

- 本地策略配置、SlotGuard reference monitor、slot 映射存储及执行服务可信。
- 身份通过所选安全机制获得并验证；消息正文里的 `recipient`、`role` 或自称身份不构成认证。
- 可研究来自工具输出和文档的不可信文本，但不假设本地操作系统已被攻陷。
- 用户授权策略是权限上限；小模型不能扩大权限。

### 4.5 不宣称解决的事项

- 已被攻陷的本地 OS、runtime 或策略存储。
- 所有 timing、size、traffic-analysis 等侧信道。
- 对保留格式、语义、频次和关系的完全隐藏。
- 已由被授权接收方获得的原始值的后续撤回。
- 任意工具、任意 shell 程序的通用安全沙箱。
- 未经实际处理的图片、音频和文件二进制内容的完整隐私保护。

### 4.6 两个不同保证

**检测性质：** 对未知敏感信息的覆盖是经验性的，会存在 false negatives。

**授权性质：** 对已注册对象和经过受控接口的操作，可以定义并验证引用作用域、权限和恢复边界。

只能在明确的假设与接口覆盖范围内证明后者，不能据此推出前者完整。

## 5. 系统架构

```text
用户策略 / 任务目标 / 本地资源
                │
                ▼
       本地工具与 Agent runtime
                │ observations / requests
                ▼
     协议感知解析与来源标记
                │
       ┌────────┴────────┐
       ▼                 ▼
   快速规则          System 1 语义模型
       └────────┬────────┘
                ▼
    候选校验 + 策略决策 + 实体关联
                ▼
       确定性替换与引用签发
                ▼
       最终出站检查 / 发送屏障
                ▼
          NLIP endpoint
════════════ 跨域信任边界 ════════════
          Remote worker
                │ operation request
                ▼
      认证绑定 + 引用/权限检查
                ▼
       本地受控执行与原始值注入
                ▼
     工具结果再次经过出站保护
```

接收端还应有独立的 **protocol-to-model projection**：认证、内部状态及不必要的协议元数据不应因方便实现而全部拼入 prompt。

### 5.1 模块划分

1. `nlip_adapter`：解析、格式分派、协议状态和原样保持职责。
2. `policy_engine`：接收方、对象、操作、任务和披露规则。
3. `semantic_advisor`：结构化本地语义建议，不直接修改输出。
4. `entity_registry`：原始值与相关形式的本地记录。
5. `reference_manager`：接收方绑定引用、过期、撤销与显式转授权。
6. `rewriter`：结构保留、FPS 与引用替换。
7. `execution_guard`：授权检查、规范化、受控执行及恢复。
8. `egress_gate`：确保审查完成后才发送，并检查所有支持的出站通道。
9. `audit`：记录决策与错误，不把原始秘密复制到外部 telemetry。

### 5.2 三个不能混淆的概念

- **实体 ID**：仅在本地使用，用于关联原始值和观察到的变体。
- **显示 slot**：让模型理解对象角色的文本表示。
- **执行授权**：由可信执行服务校验的操作权限。

显示 slot 不是权限的充分证据。即使知道合法 slot 的文本，也不能在未授权接收方、会话或操作下使用它。

## 6. 接收方绑定的引用与授权

### 6.1 拟议内部记录

以下仅为内部数据结构，不是声称 NLIP 标准已有这些字段：

```text
ReferenceRecord:
    local_object_id
    display_type
    external_handle
    authenticated_principal
    session_binding
    policy_version
    allowed_operations
    allowed_resource_scope
    expiry
    delegation_policy
    revocation_state
```

原始值与完整实体图不出本地域。对外标识符应不可预测，并有碰撞检测；具体编码方案由协议和威胁模型决定。

### 6.2 访问检查

每次受保护对象使用前，检查：

1. 当前请求来自哪个经认证 principal？
2. 引用是否属于该 principal 与允许的会话？
3. 引用是否过期、撤销或与旧策略冲突？
4. 请求操作是否在允许集合中？
5. 规范化后的目标是否处于允许范围？
6. 返回结果是否需要再次保护？

若使用签名或 MAC 保护的外部令牌，还必须考虑受众、重放、撤销及状态一致性；签名本身不解决这些问题。

### 6.3 转发和委派

第一版默认：**禁止隐式转授权**。

若 Agent A 要把工作交给 B：

- A 转发自己看到的 slot，不自动赋予 B 权限；
- 本地授权服务决定是否为 B 签发新的受限引用；
- 新权限不得超出原始权限和用户策略；
- 对 B 采用独立标识符，避免不必要的直接相等关联。

跨接收方不同标识符不能阻止根据相同内容、任务或时间进行关联；论文中需明确其保护边界。

### 6.4 路径与执行安全

- 使用平台适配的路径规范化与对象作用域检查。
- 测试符号链接、编码变体、相对路径、大小写规则及 TOCTOU 风险。
- 优先采用结构化工具调用和参数数组，而非把恢复值拼进 shell。
- 不把 shell metacharacter 黑名单当作完整执行安全机制。
- 只在最终被授权的本地执行位置注入原始秘密。

### 6.5 FPS 的额外要求

- 记录所有有意保留的元数据：类型、长度、前缀、alphabet、分隔符等。
- 区分单个 surrogate 的条件独立性与完整 transcript 的隐私。
- 检测重复 surrogate、歧义恢复及与现有值冲突。
- 不能假设“看起来像凭据”的随机串绝对不会意外有效；测试与运行环境不能让 synthetic credential 被误用于外部真实服务。
- 远端返回未注册的 credential-shaped literal 时，不自动把它认定为本地已授权凭据。

## 7. System 1 本地模型

### 7.1 模型任务

优先拆成可验证的子任务，而不是一个自由文本 sanitizer：

- 敏感 span 检测。
- 类型分类。
- 对已有实体的链接。
- 相对于任务和接收方的披露建议。
- 不确定性或升级审查标记。

### 7.2 输入

- 当前待发送片段及有限上下文。
- 经可信策略层整理的任务目标。
- 接收方信任类别，不暴露不必要的身份详情。
- 允许的保护类型、操作和披露模式。
- 本地实体注册表的必要摘要。

不能让不可信消息中的“用户已经允许披露”覆盖可信输入。

### 7.3 输出

```text
Proposal:
    message_part_id
    exact_span_or_offsets
    entity_type
    candidate_existing_entity_id
    proposed_action
    uncertainty_signal
```

运行时检查位置、原文匹配、类型、实体访问权限及允许的动作。对无效输出拒绝应用，转入预先定义的安全回退。

### 7.4 训练路线

**阶段 A：不训练。** 用若干不同规模的现成 local instruct models，测试结构化输出、检测召回、过度脱敏和延迟。

**阶段 B：分析误差。** 若主要错误稳定集中于任务条件判断、跨轮次别名或结构化边界，再建立专门数据集。

**阶段 C：有针对性的蒸馏/微调。** 使用 teacher 辅助生成，加上人工校验与程序性 ground truth。

不要只依赖 teacher 的自评标签，也不要用测试数据的模板或实体变体反向构造训练集。

### 7.5 置信度

模型自报的 confidence 不天然可靠。应使用独立校准集评估 precision/recall 与风险阈值；若采用 log-probability 或分类头，也必须验证校准及分布外行为。

### 7.6 首次出现的发送策略

| 策略 | 隐私含义 | 用途 |
|---|---|---|
| 规则后立即发送，模型后台检测 | 可能发生首次泄露 | 仅作为弱基线，不能称强隐私模式 |
| 所有候选等待模型 | 对未知内容覆盖仍取决于模型 | 建立质量上界及延迟参照 |
| 风险路由 + 阻塞审查 | 被误判低风险的内容仍可能泄露 | 研究质量—成本权衡 |
| 审查前保守遮蔽或拒绝发送 | 更强内容控制，可能损失效用 | 高风险模式 |
| 请求用户确认 | 增加交互成本 | 超出自动授权策略时 |

**硬约束：** 已标记为必须审查的内容，在结果返回前不能进入任何远端请求。超时不能悄悄切换为 raw send。

第一版不研究 speculative raw transmission，因为发送出去的信息无法通过随后替换来撤回。

## 8. Benchmark 设计

### 8.1 工作负载分层

**W1：协议与引用微测试**

- 各格式解析、子消息顺序、token 回传。
- 未知扩展与拒绝语义。
- 会话切换、重放、过期、撤销。
- 接收方替换、权限扩大和转授权。

**W2：合成隐私压力测试**

- direct、embedded、split、encoded、derived、cross-turn。
- 敏感文件名、客户名、内部系统名与 benign lookalikes。
- 规则未覆盖的形式和无关任务上下文。

**W3：真实可执行任务——论文核心**

1. 仓库调试：远端 Agent 定位并修复错误，本地执行测试。
2. 文档分析：远端组织查询，本地读取敏感文档并返回受限结果。
3. 配置与服务排障：密钥留在本地，远端规划检查步骤。
4. 多 Agent 委派：不同 worker 执行不同职责，验证不能复用对方引用。

**W4：适应性攻击**

- 全 transcript 重建。
- 连续询问收集零散信息。
- 伪造授权、协议控制指令和 slot。
- 恶意工具输出/文档中的 prompt injection。
- 转发、重放、接收方串谋及引用升级。

### 8.2 数据来源与敏感值

- 先使用许可明确的公开任务和仓库，嵌入受控敏感信息。
- 秘密使用不可用于真实账户的测试材料、沙箱服务或 canary；不收集和发布真实生产凭据。
- 如加入真实脱敏 traces，需明确授权、数据保留和人工检查流程。
- 区分“真实任务结构 + 植入隐私”与“自然产生的真实隐私”，不要混写。

### 8.3 起步规模与扩展目标

以下是预算目标，不是最终样本量承诺：

- 原型：20–30 个任务，2–3 类工作流，两个 recipient。
- 主实验候选：100–200 个独立源任务，覆盖不同任务家族。
- 随机 roots、用户、实体和接收方变体用于鲁棒性，不作为独立源任务数量宣传。
- 最终规模根据 pilot 的方差、配对差异及运行成本确定。

### 8.4 防止数据泄漏

按 repository、task family、organization/entity family 分组切分。

- 同一源任务的改写、workspace-root 变体放在同一 split。
- synthetic 模板的同族变体不能跨 train/test 造成近重复。
- 单独构建格式、实体和任务分布外集合。
- 策略阈值只能在 validation/calibration split 上调整。

### 8.5 人工标注

建立明确标注规范：

- 哪些 span 敏感。
- 对哪个接收方允许披露。
- 哪些结构可以保留。
- 有哪些可接受的替换结果。
- 什么操作被允许。

对多解样本记录多种可接受策略，并报告标注一致性及争议裁决，不强行把所有问题简化成唯一字符串答案。

## 9. 基线与消融

### 9.1 主要基线

| 基线 | 用途 |
|---|---|
| Raw + 标准认证/加密 | 原始效用与协议安全基础；不是内容隐私基线 |
| Generic redaction + 相同恢复支持 | 测量不保留结构的代价，避免故意不给恢复能力 |
| 规则 secret/PII detector + typed slots | 强化规则基线 |
| Generic local-model sanitizer | 比较自由改写与受控建议 |
| 当前 SlotGuard | 展示相对 workshop 版本的增量 |
| Protocol-aware SlotGuard，无小模型 | 隔离协议与权限设计收益 |
| Full system | 完整方法 |

VibeGuard-style 若继续使用，明确它是派生 placeholder 基线，不将结果泛化为官方系统整体表现。

### 9.2 关键公平性控制

- 使用相同主 Agent、工具、任务、模型调用预算和 retry policy。
- 结构替换比较中匹配检测覆盖；检测比较中尽量匹配替换与恢复能力。
- 协议感知比较中匹配策略及已知敏感对象，避免把更强 oracle 提供给本方法。
- 攻击测试中所有防御承受相同攻击预算。

### 9.3 消融

- serialization-level vs. protocol-aware parsing。
- session-only vs. recipient-bound references。
- 无授权检查 vs. 操作/范围授权。
- 无记忆 vs. 精确 entity table vs. 简单 SEG vs. learned linking。
- 规则 vs. 小模型 vs. 规则 + 小模型。
- task-blind vs. task-conditioned。
- block-all vs. risk-routing vs. conservative fallback。
- 不同小模型规模与量化方案。

可以先做高信息量消融，避免所有维度全交叉导致预算爆炸。

### 9.4 诊断性 oracle

加入两种非部署基线：

- oracle sensitive spans：估计检测错误之外的替换与执行上限。
- oracle policy labels：估计策略判断错误的影响。

明确它们只用于诊断，不作为可部署方法。

## 10. 指标、统计与成功标准

### 10.1 隐私指标

- **Literal exposure**：受保护值或预定义敏感组成部分出现在不允许的远端可见面中的比例。
- **Reconstructive exposure**：按预先定义的组合、编码或关联规则能恢复的值比例。
- **Attacker reconstruction success**：独立攻击者使用完整可见 transcript 恢复目标值的成功率。
- **Policy violation**：对指定 recipient 违反允许披露规则的事件比例。
- **Over-redaction**：被无必要隐藏的 benign 或任务必需内容，以及其任务代价。

分母分别报告对象、出现次数、消息、会话和任务，不用一个“leak rate”混合所有单位。

格式透露的 credential type、上下文关联和 slot 重复关系单独报告；“无显式 category label”不等于类别不可推断。

### 10.2 执行与授权指标

- 未授权操作成功率。
- 跨接收方/跨会话引用复用成功率。
- 转授权策略绕过率。
- 合法引用的错误拒绝率。
- 重放、过期和撤销检查的结果。
- 协议 conformance 与连接/会话失败率。

检测到一个敏感值与阻止一次越权操作是不同事件，分别计量。

### 10.3 效用指标

- 独立 evaluator 验证的端到端 task completion。
- 测试通过、输出文件正确性或服务状态等任务特定指标。
- 合法工具调用比例、返工与重试次数。
- 用户确认次数及额外交互轮次。

“handle selection”仅作为子指标，不替代实际任务完成率。

### 10.4 性能指标

- 本地规则、模型推理、校验、重写和授权的分阶段耗时。
- 整体任务 wall-clock latency、p50/p95。
- 冷启动与热启动。
- CPU/GPU、内存、量化、模型版本、上下文长度。
- 远端 tokens、调用次数、backoff、parse retries。
- 吞吐和并发会话下的行为。

只报告微秒 rewriting 不能支持“完整隐私层几乎无成本”的结论。

### 10.5 统计方法

- 同一任务对不同系统进行配对比较。
- 对随机生成的 root 变体按源任务/任务家族聚类处理。
- 在预算允许时重复随机种子，并分开报告任务方差和模型采样方差。
- 对 task success 和泄露率报告适当置信区间；重建攻击按同样原则处理。
- 零观测失败不写成“真实失败概率为零”；给出有限样本下的不确定性。
- 预先指定主指标及主要比较，避免只挑选有利模型或子集。

### 10.6 建议的工程与研究判断标准

以下为 pilot 决策目标，不是论文预定结果：

- 所有已定义协议和引用不变量测试必须通过；有绕过就不能称执行边界完成。
- 效用相对 Raw 的可接受损失可先定为 5 个百分点，随后结合任务风险与置信区间审视。
- 本地层热路径的端到端开销先以中位数不超过约 20% 为工程目标，且必须同时看 p95。
- 小模型必须在语义/跨轮次 held-out 集合上展示稳定增益，而非仅提高训练分布 F1。
- Full system 应在匹配威胁与预算下，相对最强相关基线改善隐私—效用 Pareto frontier。

若目标未达到，应报告并解释，不通过改变分母或删掉困难任务制造达标。

## 11. 不变量与可证明部分

可在受限接口模型下形式化：

1. **受众隔离**：只属于 A 的引用不能由 B 成功使用。
2. **权限不扩大**：执行权限不超过用户策略与已签发权限的交集。
3. **原始映射本地化**：受控发送路径不序列化原始 slot table。
4. **恢复位置限制**：原始秘密只在已授权的本地执行边界注入。
5. **先审查后发送**：被标记需要审查的消息不能先发送后决定。
6. **协议控制保持**：系统不通过内容替换破坏所采用 token/control 语义。

需要写明前提：所有相关操作都经过 reference monitor、身份验证可靠、可信组件未被攻陷、引用解析和资源规范化正确。

不把这些性质叫作完整 transcript noninterference；保留结构与上下文本身可能包含信息。

可采用单元测试、property-based tests、状态机测试及必要的小范围形式化论证。形式化不是为了证明分类器永不漏报。

## 12. 12 周推进计划

### 第 1–2 周：审计、标准映射与 pilot

任务：

- 核实当前系统及指标。
- 阅读固定版本 NLIP、binding、security profile。
- 跑通最小三方通信和 20–30 个任务。
- 建立统一事件日志与网络出口审查。
- 测试现成小模型，而非立即训练。

交付：标准映射表、威胁模型 v1、pilot 数据、关键错误分类。

**Gate A：** 若协议感知或多接收方机制没有产生可验证的新问题，缩小 NLIP 作为论文主线的比重，避免勉强包装。

### 第 3–4 周：协议边界与引用机制

任务：

- 实现 text/JSON/URI/code 分派。
- 实现 principal/session 绑定、权限、过期和撤销。
- 默认禁止隐式转授权。
- 完成 token 保持与 protocol-to-model projection。
- 实现明确发送屏障与超时回退。

交付：可运行系统、状态机/属性测试、已知不支持格式列表。

**Gate B：** 必须证明合法任务可完成，同时恶意引用测试不能绕过；否则先修执行层，不继续堆叠模型功能。

### 第 5–6 周：Benchmark 与语义组件

任务：

- 扩展独立任务和隐私标注。
- 固定 grouped splits。
- 完成 rule、generic local model、protocol-aware 无模型基线。
- 分析语义误差；决定是否做蒸馏/微调。
- 校准风险路由阈值。

交付：benchmark v1、模型选择报告、固定主实验配置。

**Gate C：** 若现成模型已足够，不训练新模型；若本地模型收益小于效用/延迟代价，保留规则与协议控制主线。

### 第 7–8 周：主要端到端实验

任务：

- 在选定的多种主 Agent/model 上执行完整任务。
- 完成核心消融和阶段延迟分析。
- 收集失败案例及真实 execution traces。
- 检查实验可复现性与 benchmark 污染。

交付：主结果表、Pareto 图、失败分类、成本报告。

### 第 9–10 周：攻击与泛化

任务：

- 完整 transcript 重建攻击。
- 引用转发、重放、权限升级和 recipient 串谋。
- 不可信文本中的 prompt injection。
- held-out repository、实体、任务族和格式测试。
- 补充 CPU-only 与并发运行结果。

交付：攻击矩阵、泛化结果、剩余限制及修复说明。

### 第 11–12 周：写作与 artifact

任务：

- 按三个主贡献组织论文。
- 将完整实现配置、prompts、模型版本和统计方法公开。
- 准备可一键运行的代表性任务和攻击测试。
- 进行独立复现与论文 claim audit。

交付：完整初稿、artifact、reproducibility checklist、投稿目标建议。

> 12 周是一个研究迭代周期，不保证完成生产级系统或所有目标实验。大规模 Agent 实验和模型训练可能需要延长。

## 13. 资源与预算管理

### 13.1 计算资源

- 本地模型：先覆盖 CPU 可运行配置和一个有 GPU 的配置。
- 主 Agent：至少选择不同能力/架构的若干模型，而非为了数量堆模型。
- 沙箱：网络出站受限、无真实凭据、可重置文件系统与服务。
- 存储：安全保存原始测试映射，公开 artifact 不含生产秘密。

### 13.2 API 预算公式

在 pilot 中实际测量：

```text
总成本 ≈ 任务数 × 条件数 × 重复次数
         × 每任务平均调用数 × 每次平均模型成本
```

攻击实验单独设上限。主实验优先跑最有信息量的比较，全面消融可以集中在代表性模型/任务上。

### 13.3 建议工作流

- 一条实现与 conformance 线。
- 一条 benchmark / evaluator / annotation 线。
- 一条实验、攻击与分析线。

若主要由一人推进，先完成最小系统和可靠评估，再扩展模型训练，不同时维护多个 transport bindings。

## 14. 主要风险与备选路线

| 风险 | 早期信号 | 应对 |
|---|---|---|
| NLIP 只成为 adapter | 去掉 NLIP 后所有结论不变 | 聚焦协议结构和授权语义，或将其降为一个部署实例 |
| 模型提升有限 | 规则已覆盖大多数样本 | 增加自然语义困难集；必要时不把训练作为贡献 |
| 延迟过高 | 小模型每轮阻塞占主要耗时 | batching、缓存、风险路由；明确剩余首次泄露风险 |
| 过度脱敏损害任务 | 频繁失败或确认 | 细化结构保留、策略粒度与本地执行接口 |
| 认证被替换破坏 | token 回传/会话测试失败 | 将控制平面与模型内容分开，遵守 endpoint 语义 |
| 引用被误当成权限 | copied slot 可越权执行 | principal 绑定与独立授权检查 |
| 攻击仍能重建 | context 足以推断敏感值 | 减少保留上下文，公开残余风险，不夸大 anonymization |
| 数据集过于合成 | Raw 近乎全满分、任务重复 | 引入独立真实源任务、自然噪声与外部分布 |
| 基线偏弱 | 无恢复、低预算、过窄 detector | 对齐能力、预算和策略，使用强规则与本地模型基线 |
| 论文内容过散 | 五六个模块各讲一点 | 以信息披露边界、受控引用、端到端证据为主线 |

### 备选 A：系统与安全主线

若引用隔离和协议处理收益强，小模型收益弱：突出跨域信息与能力边界，小模型作为可插拔检测器。

### 备选 B：任务感知模型主线

若主要收益来自语义决策，而 NLIP 特性贡献弱：以任务感知信息最小化为主，NLIP 作为真实集成环境。

### 备选 C：Benchmark 主线

若发现多 Agent 隐私评估严重缺失：先发布严格定义、真实可执行的 benchmark 与系统性分析，但避免在方法尚不成熟时过度承诺统一防御。

- 加入第二个 recipient。

- 用小规模固定集合比较规则和现成小模型。

### Day 7：Go / No-go 评审

1. 协议感知提供了什么普通脱敏没有的收益？
2. 接收方绑定解决了什么真实可复现的攻击？
3. 小模型增加的覆盖是否值得延迟与效用成本？

产出两页 pilot memo：结果、失败案例、下一阶段范围。若不能明确回答，先调整问题定义，不立即投入训练或大规模 API 实验。

---

## 17. 最终建议

**优先次序：真实端到端任务与明确威胁模型 → 协议和引用边界 → 现成小模型 → 有证据支持后再训练。**

最强的 full-paper 叙事不是“SlotGuard 支持了 NLIP”，而是：

> **协议互操作并不自动带来信息最小化。我们设计一个本地、任务与接收方感知的边界，让 Agent 能协作使用受保护对象，而不必无条件获得原始上下文或访问权限。**

这一叙事必须由协议正确性、真实执行、主动攻击和完整成本共同支撑。
